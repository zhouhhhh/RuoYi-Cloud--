## 1. 最终业务规则与范围调整

### 手机号

- 必填，格式为恰好 11 位数字，以 `1` 开头，第二位为 `3` 至 `9`。
- 新增不能使用已有手机号；修改保留自己的手机号不算重复。
- 数据库保留 `uk_customer_phone (phone)`，逻辑删除不释放手机号。
- 普通重复由业务预查提供友好提示；真正执行写入时发生的唯一冲突由
  Service 转换为业务异常，不将 SQL 和内部路径返回给调用方。

### 客户状态

| 值 | 含义 |
|---|---|
| `0` | 潜在 |
| `1` | 跟进中 |
| `2` | 已成交 |
| `3` | 已流失 |

学习者于 2026-09-02 明确修订需求：

- 状态必填，只允许上述四个值。
- 新增可选择任意合法状态；前端及数据库默认 `0` 不代表只能新增为 `0`。
- 合法状态之间允许自由修改，包括 `2 → 1` 等纠正操作。
- 不实施单向推进、终态锁定、固定初始状态或管理员审批。
- 现有新增、修改权限保持不变。

原因是客户可能在录入前已经处于其他阶段，且日常录入存在误填和判断修正。
当前已审查的客户 CRUD 链路没有因状态改变而触发合同、结算等业务副作用。
状态在此阶段是可纠正的档案属性，不是不可逆流程。原先讨论的单向流转矩阵
是被取消的候选方案，不再作为未完成项；历史进度文档中的原计划以本节为准。

- HTTP Status 为 `200`，业务 `code=500`。
- 响应包含 `Duplicate entry`、SQL、Mapper 路径和 `uk_customer_phone`。
- System 日志显示底层 `SQLIntegrityConstraintViolationException` 被转换为

## 3. 实现与职责边界

后端实现位于 `ruoyi-cloud-learning/RuoYi-Cloud-springboot3`，客户业务仍在
`ruoyi-modules/ruoyi-system`，没有拆分新服务或引入新依赖。

### 参数校验

`CrmCustomer` 的约束位于 getter，新增和修改的 Controller 请求体均保留
`@Validated @RequestBody`：

| 属性 | 约束 | 消息 |
|---|---|---|
| `phone` | `@NotBlank` | 联系电话不能为空 |
| `phone` | `@Pattern`，表达式 `^1[3-9]\d{9}$` | 请输入正确的手机号码 |
| `status` | `@NotBlank` | 状态不能为空 |
| `status` | `@Pattern`，表达式 `^[0-3]$` | 请输入正确的状态 |

正则表格表示表达式本身，Java 字符串中的反斜杠需要转义。
参数错误由现有全局参数校验异常处理返回统一响应。

前端 `ruoyi-cloud-learning/RuoYi-Cloud-Vue3-master/src/views/system/customer/index.vue`
保留手机号 required 和格式规则。为验证后端曾临时绕过前端规则；归档时
源码确认前端规则已恢复。前端校验用于交互体验，不能替代后端约束。

### 普通重复预查

```text
CrmCustomerController.add / edit
-> ICrmCustomerService.checkPhoneUnique
-> CrmCustomerServiceImpl.checkPhoneUnique
-> CrmCustomerMapper.selectCrmCustomerByPhone
-> CrmCustomerMapper.xml
```

按手机号查询只返回 `customer_id` 和 `phone`，不按 `del_flag` 过滤，与仅包含
`phone` 的唯一索引范围保持一致。新增 ID 为空时按非现有 ID 比较；查无记录
或命中自身时返回 `true`，命中其他客户时返回 `false`。

Controller 预查失败返回带客户名称的消息：

```text
新增客户'<客户名称>'失败，手机号码已存在
修改客户'<客户名称>'失败，手机号码已存在
```

预查用于提前提示，不能替代数据库唯一索引：多个请求可能在预查时同时通过。

### 写入冲突转换

`insertCrmCustomer` 和 `updateCrmCustomer` 在 Mapper 写入处捕获 Spring 的
`DuplicateKeyException`，共用私有方法 `translateDuplicateKeyException`：

1. 在服务端记录操作名称及原始异常。
2. 通过 `getMostSpecificCause()` 取得根因消息。
3. 使用空值安全的 `StringUtils.contains` 检查 `uk_customer_phone`。
4. 手机号冲突返回 `ServiceException("手机号码已存在")`；其他唯一冲突返回
   `ServiceException("客户数据存在唯一性冲突")`。

调用位置负责抛出转换后的异常，由现有全局 `handleServiceException` 生成
统一响应。本轮没有修改共享全局异常处理器，也没有将所有异常都解释为手机号重复。

## 6. 状态合法值与自由纠正验证（2026-09-02）

测试客户编号为 `test3`，手机号为 `13800000004`，接口由工具直接调用，
不依赖前端单选框约束。学习者确认本组 HTTP Status 均为 `200`。

| 请求 | 业务 code | msg |
|---|---|---|
| POST `status=null` | 500 | 状态不能为空 |
| POST `status=""` | 500 | 状态不能为空 |
| POST `status=9` | 500 | 请输入正确的状态 |
| POST `status=2` | 200 | 操作成功 |

前三次失败后的“查询未新增成功”为学习者手工确认，未附原始 COUNT 输出。
合法新增生成客户 `14/test3`，创建时间 `2026-09-02 18:01:41`。首次查询包含
ID、编号、手机号、删除标志和创建时间，但没有 `status` 列，因此不将其描述为
“新增瞬间保存为 2”的独立数据库快照。任意合法初始状态的实现依据是 Controller
和 Service 没有强制为 `0`、Mapper 接受请求状态，并有 POST `status=2` 成功响应。

之后补齐了同一客户的状态修改前后对照：

| 阶段 | 请求结果 | 数据库 status | update_by | update_time |
|---|---|---|---|---|
| 修改前快照 | 起点 | 2 | admin | 2026-09-02 18:16:41 |
| PUT 改为 `1` | code=200，操作成功 | 1 | admin | 2026-09-02 18:17:27 |
| PUT 改为 `9` | code=500，请输入正确的状态 | 1 | admin | 2026-09-02 18:17:27 |

该对照证明 `2 → 1` 的纠正操作可以成功，而非法状态 `9` 被拒绝，且该失败请求
没有改变记录的状态、更新人和更新时间。18:16:41 的快照属于本次修改起点，
不是 18:01:41 初次新增时的状态快照。

## 8. 学习结论与验收

结合学习者的解释、实现与实验，本轮学习结论为：

- 前端规则可被绕过，后端必须对外部输入建立独立的校验边界。
- Bean Validation 负责属性约束，手机号预查提供友好提示，唯一索引负责最终
  唯一性约束；预查与写入之间仍可能发生竞争。
- 捕获数据库异常不是忽略失败，而是保留服务端诊断信息并转换为可理解的响应。
- HTTP Status 与响应体业务 `code` 是不同层次，HTTP `200` 不代表业务成功。
- 验证失败是否影响数据，需要数据库前后对照，不能只看错误提示或请求字段。
- 状态合法值校验与流转限制是两类不同规则；业务允许纠正时不应强加不可逆流程。

手机号校验、重复预查、数据库兜底与异常转换，以及修订后的状态校验小闭环
均已按上述证据和边界验收。里程碑 04 完成，不再因未实现已取消的状态流转
限制而重复要求补做状态机。里程碑 05 尚未开始，本次归档不展开后续实现。
