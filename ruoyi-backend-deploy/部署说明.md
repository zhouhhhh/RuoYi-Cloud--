# RuoYi 后端独立容器部署方案（第一版）

## 范围和验证状态

面向公司内网单台 Linux 开发服务器。Mac 本地编译 JAR，Linux 构建镜像、运行七个后端服务，本地 Vue3 连接远程网关。此目录是一份待部署方案，不是已部署或生产验收结果。

已对照本地各模块 bootstrap.yml、POM、官方 docker 目录及项目根目录 docker-compose.local.yml。Compose 已通过本机 `docker compose config --quiet`，脚本已通过 `bash -n`。没有连接服务器，没有读取在线 Nacos 配置，没有执行 Maven 打包、镜像构建或容器启动；镜像拉取、配置加载、服务注册与业务链路都待现场验证。

包含：gateway、auth、system、gen、job、file、monitor。排除已有 MySQL/Redis/Nacos，以及仍在本地开发的前端。没有部署 Sentinel 或 Seata；如在线配置启用了这些能力，应先核对其依赖，不能假定此方案已覆盖。

## 文件作用

- compose.yaml：七个后端服务，每个有独立镜像标签、日志卷和容器内存上限。
- .env.example：部署变量模板，复制为 .env 后使用；不包含现有数据库和 Redis 密码。
- build/<服务>/Dockerfile：通用 Java 17 环境，将 app.jar 复制到镜像内。
- stage-jars.sh：把本地已打包 JAR 收集到七个构建目录；可以只收集 system。
- 不挂载 /app 或 JAR，避免旧卷遮住新应用；日志挂载 /app/logs，File 上传文件挂载 /data/uploads。

## 设计和启动前必须确认的内容

1. 本地基础设施文件声明服务器为 192.168.106.199，网络名为 ruoyi-cloud-learning-local，Nacos 容器名为 rcl-nacos。这只是本地配置证据，先在 Linux 验证实际环境：

   ```bash
   docker compose version
   docker network inspect ruoyi-cloud-learning-local
   docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
   free -h
   df -h
   ```

   外部网络必须已经存在，且现有 Nacos/MySQL/Redis 接入该网络。不要为通过启动而盲目新建一个同名空网络。此 Compose 接入现有网络，但不管理它和基础设施容器。

2. Compose 通过启动参数统一覆盖 Nacos 配置和注册中心地址，解决 Job/File/Monitor 源码仍写 localhost 的问题。默认连接 rcl-nacos:8848。命名空间填 Nacos 的 namespace ID；空值表示 public。默认 dev + DEFAULT_GROUP，便于沿用已有开发配置。

3. 在 Nacos 确认下列配置存在，且与项目要求一致：

   ```text
   application-dev.yml
   ruoyi-gateway-dev.yml
   ruoyi-auth-dev.yml
   ruoyi-system-dev.yml
   ruoyi-gen-dev.yml
   ruoyi-job-dev.yml
   ruoyi-file-dev.yml
   ruoyi-monitor-dev.yml
   ```

   数据库/Redis 地址必须能从应用容器访问，不能写 127.0.0.1。可以用已核实的容器名 rcl-mysql:3306、rcl-redis:6379（同网络），也可以继续使用可达的服务器内网地址。数据库名、账号和密码保持真实配置，不从模板猜测。检查是否有固定的 Nacos 注册 IP、网卡配置或本机路径，避免覆盖容器自动选择的地址。

4. 同一命名空间、同一组下，旧本地实例和新容器实例可能一起参与负载均衡。首次切换应停止 Mac 上对应 Java 服务，等 Nacos 移除旧实例再验证；否则请求可能一部分仍落到 Mac。以后临时本地调试也需处理这个问题，或建立独立命名空间并配套隔离网关和业务服务。容器注册桥接 IP 是本方案的预期行为，网关和各业务服务同网络可以互访，不应强行全部注册成宿主机 IP。

5. Job 首次启动前检查数据库里的定时任务，确认没有不希望执行的任务。所有模块常驻意味着 Job 会按实际配置执行任务。Monitor 核对登录配置，能打开页面不代表所有服务都已接入监控。

6. File 采用现有 LocalSysFileService 时，需核对有效配置为 file.path=/data/uploads、file.prefix=/statics、file.domain=http://服务器IP:9300。本版用命令行参数明确指定这三个值，仍应核对日志和实际上传后的路径、URL。检查 referer.allowed-domains 包含实际前端来源，不要简单关闭过滤。若选择了 MinIO/OSS 实现，持久化与访问域名应按对应实现另配。

7. 网关原 bootstrap 含 Sentinel 控制台 localhost:8718。本版通过 SPRING_CLOUD_SENTINEL_ENABLED=false 暂不启用 Sentinel；因此不提供 Sentinel 限流保护。后续需要时配置可达控制台、规则数据源，再开启。

8. 暂定六个服务各 1 GiB 容器上限、System 1.5 GiB，总上限 7.5 GiB；堆分别 512 MiB / 768 MiB。不是实测需求或保证能启动的容量。还需给 MySQL、Nacos、Redis、操作系统留空间，按服务器余量、GC 和 OOM 证据调整，不能把 Xmx 等同进程总内存。

9. 只发布服务器内网 IP 上的 8080（网关）、9300（文件直链）、9100（监控）；其他服务仅容器内访问。内网访问控制沿用公司的要求，发布端口不代表已经做身份验证。检查这些端口未被占用。普通 CRUD、Auth 等请求走网关；前端直接调用某业务端口的旧写法需要改为网关。

10. Java 由镜像提供，服务器宿主机不需要另装 JDK/Maven。镜像默认 eclipse-temurin:17-jre-jammy；首次需要能拉取基础镜像，或提前从可联网的同架构 Linux 环境导入/使用公司镜像仓库。正式固定版本时将 JAVA_IMAGE 改为审核过的精确标签或摘要。镜像在 Linux 服务器构建，避免 Mac ARM 与服务器 AMD64 镜像架构不一致。

## 一、Mac 本地打包并收集 JAR

在后端项目根目录执行：

```bash
cd '/Users/zhou/Documents/RuoYi-Cloud熟练/ruoyi-cloud-learning/RuoYi-Cloud-springboot3'
mvn clean package
```

正常执行测试并打包；如明确选择跳过测试，需记录“仅打包，测试未执行”，不能当作测试通过。

在本交付目录执行：

```bash
bash stage-jars.sh '/Users/zhou/Documents/RuoYi-Cloud熟练/ruoyi-cloud-learning/RuoYi-Cloud-springboot3' all
```

脚本先检查七个 JAR 是否都存在且非空，再复制为 build/<服务>/app.jar，打印 SHA-256。脚本不打包也不操作服务器。

## 二、上传部署目录

以下命令中的 用户名 替换成你实际 SSH 用户。服务器目录使用该用户自己的 ~/ruoyi-backend-deploy。

Mac 上，在本交付目录执行：

```bash
ssh 用户名@192.168.106.199 'mkdir -p ~/ruoyi-backend-deploy'
rsync -av --exclude='.env' ./ 用户名@192.168.106.199:~/ruoyi-backend-deploy/
```

随后登录 Linux：

```bash
ssh 用户名@192.168.106.199
cd ~/ruoyi-backend-deploy
cp .env.example .env
chmod 600 .env
```

仅第一次复制 .env，已有部署不要覆盖。编辑 .env 核对服务器 IP、网络、Nacos 等变量，并把七个 VERSION 改为本次唯一版本（例如 20260924-01）。同版本标签不要用于不同构建。数据库/Redis 配置依然来自 Nacos。

## 三、第一次构建与启动

确认前述 Nacos 配置和现有基础设施后，在 Linux 部署目录执行：

```bash
docker compose config --quiet
docker compose build
docker compose up -d --no-build --pull never
docker compose ps
docker compose logs --tail=100 gateway auth system gen job file monitor
```

不需要执行官方 deploy.sh，也不执行基础设施的 down。七个应用独立启动；本文件没有对另一个 Compose 项目的基础设施添加虚假的 depends_on。必须先确认基础设施已就绪。

容器 Running 只说明主进程尚在，不等于业务就绪。本版没有伪装成业务健康检查的端口探测，应结合启动日志、Nacos、实际接口判定。

## 四、前端切换和验收

Mac 上在 Vue3 项目 vite.config 中找到 /dev-api 代理，将 target 从 http://localhost:8080 改成 http://192.168.106.199:8080，保留原有前缀重写逻辑，重启前端开发服务。浏览器侧接口基地址仍可保持 /dev-api，不需要到处替换 API 文件。

先检查 Nacos 七个应用实例健康，实例地址属于本 Docker 网络，且已无不需要的本地实例。然后至少验证：

- 验证码、登录、获取用户和菜单。
- System 客户/联系人列表和一次新增或编辑；保留 Network 与日志证据。
- Gen 读取表及生成代码流程。
- File 上传后返回 URL 可从 Mac 打开；重建 File 容器后旧文件仍可访问。
- Job 只对已确认的测试任务验证，不盲目触发现有业务任务。
- Monitor 页面和预期服务监控信息。

本地 Mac 不再启动这些 Java 服务；只有前端与开发工具常驻。

## 五、日常只更新 System

Mac 后端根目录：

```bash
mvn -pl ruoyi-modules/ruoyi-system -am clean package
```

`-am` 同时构建 System 需要的本工程依赖。若实际修改了 common/api 并影响其他服务，这些服务也必须重新打包部署；不能因为只更新 System 就假定其他服务自动获得公共代码修改。

Mac 本交付目录：

```bash
bash stage-jars.sh '/Users/zhou/Documents/RuoYi-Cloud熟练/ruoyi-cloud-learning/RuoYi-Cloud-springboot3' system
scp build/system/app.jar 用户名@192.168.106.199:~/ruoyi-backend-deploy/build/system/app.jar.next
```

上传到临时文件名不会影响正在运行的镜像。Linux 部署目录：

```bash
sha256sum build/system/app.jar.next
cp .env .env.before-system-update
mv build/system/app.jar.next build/system/app.jar
```

校验值要和本地脚本打印的一致。随后手工编辑 .env，只把 SYSTEM_VERSION 改为新唯一版本，例如 20260924-02，其余版本保持不变。执行：

```bash
docker compose build system
docker compose up -d --no-deps --no-build --pull never system
docker compose logs --tail=100 system
```

必须确认 build 成功再执行 up。此时 Gen/Auth/Gateway 等保持原镜像和容器，System 会有单实例重建的短暂中断。浏览器复测修改的功能和登录后的基本请求，不能只看启动日志。不要使用 restart 来代替应用新镜像。

## 六、回滚 System

保留旧标签镜像，不在验证前执行 image prune。将 .env 的 SYSTEM_VERSION 改回上次版本，确认旧镜像存在：

```bash
docker image ls ruoyi-learning/system
docker compose up -d --no-deps --no-build --pull never system
```

这里刻意不 build；即使 build/system/app.jar 已是新版，仍启动指定的旧镜像。回滚只影响应用，不撤销数据库结构或数据变更；涉及 SQL 时需单独安排兼容性和数据恢复。

## 七、运行维护

```bash
docker compose ps
docker compose logs --tail=200 system
docker compose logs -f system
docker stats --no-stream
docker compose restart gen
```

restart 适用于重启同版本服务，不用于应用新镜像或新 Compose 配置。restart 策略只处理进程退出等场景，不监控 JAR 变化，也不保证自动修复业务异常。

本版采用 Docker 命名卷保存各服务文件日志和上传文件。json-file 日志配置有轮转，但应用自身写入的日志仍按项目 logback 策略执行，需关注磁盘增长。不要删除 file-uploads 卷；不执行 `docker compose down -v`。镜像升级不应该清理业务数据卷。
